# Freeway Benchmark Protocol

This protocol defines how benchmark results are collected and how they are used.
If a run does not follow this protocol, its numbers are for reference only and must
not be used for design decisions.

## 1. Scope

- `JMH` benchmarks measure isolated hot paths inside the JVM.
- Black-box HTTP benchmarks measure end-to-end request handling.
- The in-repo smoke harness is for local validation and regression detection.
- Final performance comparisons should use the separate-process HTTP benchmark
  or an external tool under the same workload, same commit range, and same protocol.

## 2. Environment Lock

Record the following for every benchmark report:

- commit SHA
- branch name
- JDK vendor and exact build
- OS version
- CPU model
- physical core count
- RAM size
- GC settings
- heap size and JVM flags
- benchmark module version

Keep these conditions stable across comparison runs:

- same machine
- same power mode
- no background load if it can be avoided
- same JDK build
- same JVM flags
- same input data
- same route set / same SQL / same payloads

## 3. JMH Protocol

Default JMH settings for freeway microbenchmarks:

- forks: 2
- warmup iterations: 5
- measurement iterations: 5
- warmup time: 1s
- measurement time: 1s
- mode: `thrpt`

Use `avgt` only when you are explicitly investigating latency-like cost per operation.
If the benchmark is allocation-sensitive, add `-prof gc`.

These defaults live on the benchmark classes themselves (`@BenchmarkMode`,
`@OutputTimeUnit`, `@Warmup`, `@Measurement`, `@Fork`), so a plain invocation with no
strategy options follows the protocol:

```bash
CP="target/classes:$(cat target/benchmark.classpath)"
java -cp "$CP" org.openjdk.jmh.Main \
  'com.jujin.freeway.bench.jmh.RouteIndexBenchmark'
```

`exec:java` does not propagate the forked-runner classpath (`ForkedMain` is
missing there), so benchmarks always run through a plain `java` process — which
is also what the protocol wants (a fresh JVM per run). The
`benchmark.classpath` file is generated by the `benchmark-classpath` execution
in this module's pom on every build, so rebuild before benchmarking.

Command-line options still override the annotations (`-f`, `-wi`, `-i`, `-bm`), which is how
local iteration is done. A run whose options differ from the block above does not follow this
protocol: its numbers are reference only, and the recorded options must say so.

Rules:

- run candidate and baseline with identical JMH options
- use a fresh JVM process for each run
- do not mix benchmark classes in a single ad hoc invocation unless the comparison requires it
- do not compare numbers collected with different forks, different warmup lengths, or different payloads

## 4. HTTP Black-Box Protocol

Design numbers come from split runs only: `bench suite --fork` (one resident server
plus one client per cell, spawned by the established `BenchFork` path — the `READY
port=` handshake both sides already spoke). Sharing one JVM between server and load
generator (`run`/`suite` without `--fork`) is the smoke shape, and its numbers are
reference only even with warmup and median.

Each design cell runs with:

- one fixed endpoint set, one fixed request shape, one fixed concurrency level
- a fixed count of warmup requests, discarded before measurement
- at least 3 measured rounds against that same server (8 with warmup 20000 is the
  standing practice — rounds must flatten; see the climb rule below)
- a pause between the warmup and each measured round (`--pause-millis`, 0 disables)
- median summary over the **last 5** measured rounds (`--median-last=5`, the standing
  table's method): early rounds measure the JIT ramp, not the engine — `stillClimbing`
  warns about exactly that — so the tail is the signal. `--median-last=0` is the
  full-window median, kept for comparison; the two are quoted together when they differ.
  The per-cell line names its window (`[median last 5 of 8]`), medians each field, and
  reports an rps that is by construction the round the suite persists as the cell's
  representative — the two medians in one run's output are one reading, not two.
- disjoint cores where taskset exists (`--taskset-server/--taskset-client`; a single
  inherited mask cannot express split pinning)

Rules that fail loudly instead of recording bad data:

- unmeasurable cells never boot: `ECHO_BODY` has no sending client in any mode, so
  `run`/`suite` reject it up front with a usage error — no server boot, no zero rows.
- a cell with zero successful requests across all rounds aborts with an exception, not
  a persisted zero median. Partial errors stay recorded; they are signal, not breakage.
- a generator averaging at or above 75% client CPU invalidates its rounds (exit code 2).
  The gate only runs on split shapes — sharing a JVM with the server reports both sides
  at once, so the reading means nothing there.
- rounds that still climb (max/min spread over the last five above a quarter) print a
  WARN and the median is read as under-reporting: warmup goes up, not the round count.

Threading models are not forced equal: Undertow XNIO sizing is explicit
(`-Dbench.io-threads=N`, default every processor, effective value quoted from the
run); Jetty runs its own pool defaults. Record each engine's shape in the report
instead of pretending one knob fits all.

Hygiene for official runs: `clean` build first (a stale `target/` has hidden ABI
breaks before), `repro.sh` for the full matrix (`--dry-run` prints every command),
results JSON (`-rf json`) beside the report under `docs/`.

Explicitly out of scope (decided, not overlooked): a Dockerfile — no daemon here to
verify one, and the environment lock above is the portable substitute.

For final comparisons, external tools such as `wrk2` for HTTP/1.1 and `h2load`
for HTTP/2/TLS are still preferred when available: `wrk -t4 -c100 -d60s --latency
http://127.0.0.1:<port>/ping` (or `wrk2 -R` for rate-shaped load) against any
resident server, paste the numbers next to the harness ones — agreement is the
check, the harness alone is a single witness.

## 5. Comparison Rules

- Use at least 3 measured rounds for a black-box comparison.
- Prefer the median round when summarizing.
- Report both absolute values and relative delta.
- If the change is below 3 percent, treat it as noise until it is reproduced.
- If p95 or p99 regresses by more than 5 percent, investigate before merging.
